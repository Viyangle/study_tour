# 反馈闭环留出实验（合成数据）

> 这是本地实验，不是真实用户数据。实验结束后已清空 `tag_feedback_event`，并把 `attraction_tag.pos/neg` 恢复为 0；本文档保留过程和结果。

## 协议

> 注意：本实验是在「旧版：每一轮 ADD/KEEP/REMOVE 立即计分」语义下跑的历史结果，用于说明旧规则的风险。当前代码已改为「中间轮次只记录、最终发布结算」（CONFIRM +0.8 / REJECT -0.2），尚未用真实发布数据复测。

- 数据：本地 `study_tour` 库，300 条有 tag 的历史路线，50 个 ACTIVE 景点；
- 留出：`route_id % 5 == 0` 为测试集（59 条路线，平均 2.98 个有效站点），其余 235 条为训练集；
- 反馈：训练集每条路线，对每个站点生成一条 `ROUTE_STOP_ADD`，权重 0.6，意图为该路线的 `tag`；
- 账号：映射到已有账号，受 `user-cap-30d=0.8` 约束；
- 应用：启动真实 `TagFeedbackProcessor`（1s 间隔），711 条事件全部 APPLIED；
- 评估：测试集路线按对应 tag 对 50 个候选景点排序，relevance 为路线站点，比较 prior 权重和 feedback 后 `effective_weight`。

## 结果

| 指标 | 反馈前 | 反馈后 | 变化 |
|---|---:|---:|---:|
| Recall@3 | 0.0593 | 0.0424 | **-0.0169** |
| NDCG@3 | 0.0521 | 0.0365 | **-0.0156（-30.0%）** |
| MRR@3 | 0.0876 | 0.0593 | -0.0283 |
| Recall@5 | 0.0847 | 0.0565 | -0.0282 |
| NDCG@5 | 0.0661 | 0.0446 | -0.0216 |
| MRR@5 | 0.1062 | 0.0720 | -0.0342 |
| Recall@10 | 0.1963 | 0.1850 | -0.0113 |
| NDCG@10 | 0.1147 | 0.1005 | -0.0142 |
| MRR@10 | 0.1337 | 0.1057 | -0.0280 |

逐路线 NDCG@3：

```text
improved = 2
unchanged = 52
worse = 5
```

这个下降不是所有路线一起变差，而是少数路线的排序被明显打乱，拉低了平均。

权重影响：

```text
changed rows = 188 / 225（83.6%）
average |delta| = 0.111
max |delta| = 0.304
```

## 真实 API 流程验证

另外用真实 token 跑了一条完整会话：

```text
第 1 次生成：session-history-001 -> route 605
第 2 次生成：同 memoryId，改需求 -> route 605 更新
发布：POST /routes/605/publish -> project 3316
```

中间两轮生成后：

```text
tag_feedback_event = 0
```

发布结算后：

```text
ROUTE_STOP_CONFIRM  4 条  +0.8  APPLIED
ROUTE_STOP_REJECT   3 条  -0.2  APPLIED
PROJECT_PUBLISH     1 条          IGNORED preference-only
```

最终 4 个站点的权重变化（示例）：

```text
历史人文 0.950 -> 0.960（+0.010）
科技探索 0.450 -> 0.546（+0.096）
历史人文 0.900 -> 0.920（+0.020）
博物馆研学 0.950 -> 0.955（+0.005）
```

说明：

- 中间轮次确实没有提前加分；
- 发布时只有最终路线拿到正向；
- 被淘汰的 3 个过程景点拿到 -0.2 的轻降；
- 单用户幅度很小，符合「过程不确定、最终才确认」的语义；
- 这条测试数据已清理（route/project/events/pos-neg 全部删除）。

## 旧实验的用户视角补充

把训练集出现次数最高的 10 个景点定义为「常见」，其余 40 个为「小众」：

| 指标（K=10） | 反馈前 | 反馈后 | 变化 |
|---|---:|---:|---:|
| 常见景点 Recall@10 | 0.1186 | 0.1186 | 0 |
| 小众景点 Recall@10 | 0.4576 | 0.4237 | **-0.0339** |
| Top10 平均历史出现次数 | 155.93 | 156.66 | +0.73 |
| Top10 覆盖景点数 | 46 | 47 | +1 |
| 手动目标景点平均名次 | 25.74 | 26.11 | **+0.37（变差）** |
| 手动目标进入 Top10 | 34/176 | 32/176 | -2 |

解释：

- 「常见景点被推高」确实发生了一点，但只有 **+0.73** 的平均历史频次，幅度很小；
- 代价是小众景点 Recall@10 下降 3.4 个百分点；
- 用户手动想选的景点平均排名反而从 25.74 降到 26.11，Top10 命中少 2 个；
- 所以即使按「常见优先、手动补选」的产品目标，当前反馈也没有表现出足够收益。

## 结论

1. **这组合成反馈没有证明有用，反而在留出集上变差。** 当前「路线里出现过的景点就加正向证据」过于粗糙，容易把训练集里常见、但测试集并不需要的景点推高。
2. 实验只做了正向 `ROUTE_STOP_ADD`，没有真实的「移除/保留」负向和筛选，因此不能等同于真实迭代反馈；但它足以说明：**不能把当前规则直接应用到生产权重**。
3. 常见景点提升幅度（+0.73 平均频次）不足以抵消小众召回和手动选择排名的下降；手动选择仍然可用，但反馈没有让它更容易。
4. 因此新增 `app.tag-vector.apply-enabled=false`：默认只采集事件，不自动改 `pos/neg`；需要验证时才手动打开。
5. 用户手动提交/编辑路线现在也会被 `RouteIterationFeedbackService.recordSubmission` 捕获，后续真实数据可以区分「AI 生成变化」和「用户手动增删」。
