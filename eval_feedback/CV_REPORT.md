# 景点标签反馈闭环评估报告

> 评估对象：路线会话最终结算（`ROUTE_STOP_CONFIRM +0.8` / `ROUTE_STOP_REJECT -0.2`）
> 数据来源：本地 `study_tour` 历史路线离线重放 + 一次真实 API 流程
> 结论先行：**工程链路跑通；反馈能显著提升「最终站点 vs 过程淘汰站点」的 pairwise 准确率（0.090→0.313），但整体 NDCG/常见度没有提升，尚不能作为产品级有效性证明。**

## 1. 实验目的

回答两个问题：

1. 用户反复生成路线、最终发布后，用「最终站点正向、过程淘汰站点轻降」更新景点 tag，是否能让后续路线排序更接近用户最终选择？
2. 对单个用户的影响是否足够小，不会因为一个人改路线而大幅改变全库 tag？

## 2. 数据与协议

| 项 | 设置 |
|---|---|
| 数据 | 本地 300 条有 tag 的历史路线，50 个 ACTIVE 景点 |
| 验证 | 5 折交叉验证，按 `route_id % 5` 分折；每折约 235 训练 / 59 测试 |
| 每折训练会话 | 训练路线作为一次最终发布会话 |
| 正向 | 最终路线上的站点：`ROUTE_STOP_CONFIRM +0.8` |
| 负向 | 从该 tag 的 prior Top 候选中选 2 个未进最终路线的「硬负例」：`ROUTE_STOP_REJECT -0.2` |
| credit | 与 `TagFeedbackProcessor` 一致：`(0.05+intent_i)·s_i` 归一化 |
| 单用户上限 | 0.8 / 景点 / 30 天 |
| 衰减 | 无（同一时刻重放） |
| 评估 | 测试路线站点为 relevance，对 50 个候选按对应 tag 权重排序 |

> 这是离线重放，不是真实用户数据；硬负例是按 prior 排名构造的，真实用户淘汰原因可能不同。

## 3. 5 折结果

| 指标 | 反馈前均值 | 反馈后均值 | Δ 均值 | Δ 标准差 | 正向折数 |
|---|---:|---:|---:|---:|---:|
| Recall@5 | 0.1161 | 0.1031 | **-0.0130** | 0.0206 | 1/5 |
| NDCG@5 | 0.0980 | 0.0881 | **-0.0099** | 0.0220 | 2/5 |
| MRR@5 | 0.2090 | 0.2021 | -0.0070 | 0.0373 | 2/5 |
| Recall@10 | 0.2353 | 0.2163 | **-0.0191** | 0.0163 | 1/5 |
| NDCG@10 | 0.1510 | 0.1394 | **-0.0116** | 0.0198 | 2/5 |
| MRR@10 | 0.2090 | 0.2021 | -0.0070 | 0.0373 | 2/5 |

95% 置信区间（按 5 折均值，t=2.776）：

```text
NDCG@5  Δ = -0.0099，95% CI [-0.0373, +0.0174]
NDCG@10 Δ = -0.0116，95% CI [-0.0362, +0.0130]
Recall@10 Δ = -0.0191，95% CI [-0.0393, +0.0012]
```

区间都跨 0，不能宣称显著提升；点估计方向为负。

## 3.1 换成更贴近目标的指标

标准 Recall/NDCG 把未进历史路线的景点都当负例，偏严。补两个指标：

- **Pairwise accuracy**：对每个测试路线，比较「最终路线站点」与「过程中淘汰的硬负例」，看最终站点得分是否更高；
- **Graded NDCG**：最终站点 relevance=1，常见景点 relevance=0.3，其余 0；不再把常见景点当完全错误。

| 指标 | 反馈前 | 反馈后 | Δ | 正向折数 |
|---|---:|---:|---:|---:|
| Pairwise accuracy | 0.0902 | 0.3130 | **+0.2228** | 5/5 |
| Graded NDCG@5 | 0.1976 | 0.1555 | **-0.0422** | 0/5 |
| Graded NDCG@10 | 0.2570 | 0.2292 | **-0.0278** | 0/5 |
| Top10 平均常见度 | 15.28 | 15.23 | -0.055 | — |

95% CI（5 折，t=2.776）：

```text
Pairwise     Δ = +0.2228，95% CI [+0.1858, +0.2598]
Graded NDCG@5  Δ = -0.0422，95% CI [-0.0586, -0.0258]
Graded NDCG@10 Δ = -0.0278，95% CI [-0.0359, -0.0197]
```

Pairwise 的 5 折全部正向，且区间不跨 0；Graded NDCG 的 5 折全部负向，区间也不跨 0。两者方向相反，说明反馈确实在优化「最终 vs 淘汰」，但这个优化伤害了整体排序和常见景点覆盖。

逐折 pairwise：

| fold | 前 | 后 | Δ |
|---:|---:|---:|---:|
| 0 | 0.053 | 0.258 | +0.205 |
| 1 | 0.085 | 0.306 | +0.221 |
| 2 | 0.116 | 0.388 | +0.272 |
| 3 | 0.075 | 0.298 | +0.223 |
| 4 | 0.122 | 0.316 | +0.194 |

这说明：

- 反馈**确实学到了目标方向**：最终站点相对过程淘汰站点的 pairwise 准确率从 0.090 提到 0.313，5 折全部提升；
- 但绝对水平仍只有 **0.313**，远低于 0.5，意味着多数「最终 vs 淘汰」配对仍然排反；
- 这个局部提升没有转化为整体 graded NDCG（反而下降），Top10 常见度也基本不变。

所以数据更准确的表述是：

> 反馈在「最终站点 vs 过程淘汰站点」这个训练目标上有明显学习效果，但不足以改善整体路线候选排序，也没有提升常见景点覆盖；不能作为产品级有效性证明。

## 4. 真实 API 流程验证

除了离线重放，还用真实 token 跑了一次完整会话：

```text
第 1 次生成：session-history-001 -> route 605
第 2 次生成：同一 memoryId，改需求 -> route 605 更新
发布：POST /routes/605/publish -> project 3316
```

中间两轮生成后：

```text
tag_feedback_event = 0
```

发布结算后：

```text
ROUTE_STOP_CONFIRM  4 条  +0.8  APPLIED
ROUTE_STOP_REJECT   3 条  -0.2  APPLIED
PROJECT_PUBLISH     1 条        IGNORED preference-only
```

最终 4 个站点的权重变化示例：

```text
历史人文   0.950 -> 0.960  (+0.010)
科技探索   0.450 -> 0.546  (+0.096)
历史人文   0.900 -> 0.920  (+0.020)
博物馆研学 0.950 -> 0.955  (+0.005)
```

说明工程链路和「最终才加分」的语义正确，单用户影响约 ±0.1 级别；但因为只影响少量景点，这个幅度通常不足以改变 Top10。

## 5. 结论

1. **反馈有局部学习效果，但没有形成端到端提升。** 5 折 pairwise accuracy 从 0.090 提升到 0.313（+0.223，5/5 折正向），说明「最终 vs 淘汰」这个训练目标确实被学到了；但 graded NDCG 和 Top10 常见度没有提升，标准 NDCG 仍为负，且 pairwise 绝对值只有 0.313（低于 0.5）。
2. **工程实现是完整的**：中间轮次不计分、最终发布结算、淘汰轻降、显式纠正、单用户上限、偏好事件隔离都工作正常。
3. **原因判断**：把「一次会话的最终选择」写成全局景点-tag 权重，会把会话特定偏好当成景点属性；训练路线和测试路线的最终站点并不一致，全局权重容易过拟合。
4. **建议保持 `apply-enabled=false`**：保留事件采集，不自动改权重；这个功能目前适合作为数据埋点，而不是线上排序器。

## 6. 如果导师要求「有用」的方向

当前数据结构下，更可能有收益的做法：

1. **会话级/用户级 reranker**：最终确认只影响这个用户下一轮，不写全局 tag 先验；
2. **popularity 独立分**：常见景点走热度特征，不混进语义 tag；
3. **混合排序**：`final_score = tag_match + popularity + session_preference`，再做 A/B；
4. 等真实的多轮生成日志（不是历史路线重放）再做一次留出评估，避免硬负例构造偏差。
