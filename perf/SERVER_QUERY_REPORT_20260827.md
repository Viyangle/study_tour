# 后端查询性能初测报告（2026-08-27）

## 1. 测试结论

服务器在 1,234 条项目数据下完成了 4 组查询测试。全部计时请求共 2,540 次，HTTP 与业务错误均为 0，说明接口在本轮负载范围内保持稳定。

主要结论：

1. 首页第一页项目推荐在 4 并发时 P95 为 209 ms、吞吐 24.3 req/s；8 并发时 P95 为 398 ms、吞吐 24.2 req/s，已出现吞吐平台。
2. 项目数据库筛选在 8 并发时 P95 为 591 ms、吞吐 18.2 req/s；16 并发时 P95 升至 1.05 s，吞吐仅增至 19.6 req/s；32 并发吞吐反降。
3. 首页推荐访问第 1～5 页时延迟明显高于固定第一页，表明推荐计算成本会随页码增大。
4. 8 并发混合负载持续 60 秒无错误，但 P95 为 4.11 s；拆分后长尾主要来自项目推荐及推荐理由，普通筛选、路线和景点查询 P95 均低于 0.5 s。

按常见体验目标判断：

- 以 P95 < 500 ms 为目标：首页第一页可支持约 8 个同时在途请求；项目筛选建议不超过 4 并发。
- 以 P95 < 1 s 为目标：首页第一页可支持约 16 并发；项目筛选建议不超过 8 并发。
- 为生产环境保留余量时，首页推荐建议以 4 并发作为舒适区，筛选查询建议以 4～8 并发作为舒适区。

## 2. 测试条件

- 目标服务：`http://47.94.95.110:8080`，自动跳转 HTTPS。
- 测试账号：填充数据中的普通用户账号。
- 数据规模：项目 1,234、路线 301、路线景点关系 899、账号 245、项目成员关系 5,496。
- 测试方式：客户端通过公网访问服务器，使用 HTTP keep-alive；结果包含网络、JWT、控制器、业务逻辑、数据库及响应传输时间。
- 并发阶梯：每档预热 2 秒、计时 10 秒，档位之间冷却 1.5 秒。
- 持续负载：8 并发、计时 60 秒。
- 成功标准：HTTP 200 且响应业务码 `code=1`。

本报告是服务器更新后的快速初测。阶梯档位仅持续 10 秒，适合发现趋势和瓶颈；正式论文或答辩数据建议每档持续 30 秒并独立重复 3 轮。

## 7. 解释与改进方向

1. 当前结果是公网端到端响应时间，不是 MySQL 单独的 SQL 执行时间。景点等轻量接口约 0.15～0.3 秒，可视为网络、认证、日志和框架开销的参考基线。若要汇报纯数据库耗时，应增加同机/VPC 发压及 MySQL `EXPLAIN ANALYZE`、慢查询记录。
2. 首页推荐第一页表现良好，深页性能是更明显的问题。可缓存短时间内相同用户的推荐结果，或一次计算较大候选集后在缓存中分页，避免每次翻页重新执行 PageRank/MMR。
3. 当前配置启用了 MyBatis `StdOutImpl` SQL 明细输出，控制器与拦截器也会逐请求记录日志。高并发下日志格式化与磁盘/控制台 I/O 可能放大延迟；正式性能测试应关闭 SQL 明细日志，并保留必要的汇总监控。
4. 项目筛选在 8～16 并发间饱和。下一步可对实际 SQL 执行 `EXPLAIN ANALYZE`，检查 `status`、`region_adcode`、`created_at` 的组合索引和排序是否产生 filesort，再做索引前后对照测试。
5. 正式报告应同时采集服务器 CPU、内存、GC、Tomcat 工作线程、Druid 连接池活跃/等待连接及 MySQL 慢查询，这样才能把吞吐平台准确归因到 CPU、线程池、数据库连接池或 SQL。

## 8. 正式复测建议

在保持相同数据和配置的前提下：

1. 首页第一页：并发 `1,2,4,8,16`，每档 30 秒，重复 3 轮。
2. 项目筛选：并发 `1,2,4,8,16,32`，每档 30 秒，重复 3 轮。
3. 混合稳定性：8 并发持续 5 分钟；若 P95 目标允许，再增加 16 并发对照。
4. 分别保留“当前日志配置”和“关闭 SQL 明细日志”两组结果，量化日志开销。
5. 最终结论注明硬件、JDK、MySQL、网络位置、项目数量及测试日期。
