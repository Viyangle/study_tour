# 普通查询 / 项目推荐性能复测（2026-09-01）

## 结论

本轮在与 2026-08-27 基线相同的服务器、账号、接口参数和快速测试时长下，共完成 3,271 个计时请求，HTTP 与业务错误均为 0。

- 新版项目推荐链路稳定，但首页第一页性能明显回退：4～16 并发下平均耗时增加 35%～39%（16 并发为 35%），P95 增加 27%～41%，吞吐下降 26%～28%。
- 首页推荐峰值吞吐由约 24.3 req/s 降至 18.1 req/s，下降约 25.6%。
- 以 P95 < 500 ms 为目标，建议并发由旧版的 8 降到 4；以 P95 < 1 s 为目标，建议并发由旧版的 16 降到 8。
- 数据库项目筛选对照显著变快：8 并发 P95 从 591 ms 降到 283 ms、吞吐从 18.2 升到 37.2 req/s。因此推荐链路的回退不太像公网或服务器整体变慢。
- 8 并发、60 秒混合流量的吞吐基本不变（6.15 → 6.09 req/s），但整体 P95 上升 10.9%；项目推荐和带理由推荐仍是长尾来源。

本轮是单轮快速复测，每个阶梯只计时 10 秒；结论适合定位趋势，不替代 30 秒 × 3 轮的正式基准。

## 建议

1. 优先对项目推荐请求做 CPU profiling 或分段计时，分别记录相似用户计算、Personalized PageRank、全项目打分和 MMR 的耗时。
2. 当前代码每次请求都会重新构造 PPR 出边并执行最多 30 轮迭代，同时 MMR 会遍历候选集；若新版引入更多语义边，PPR 出边数量和每轮传播成本是首要排查点。
3. 对同一用户的 PPR 或最终推荐 ID 列表做短时缓存，再从缓存分页，可同时改善首页并发和深页长尾。
4. 修正压测脚本，在原始 CSV 中记录 `pageNum`，然后补跑固定第 1、3、5 页，避免随机页码分布干扰版本对比。
5. 正式确认前按每档 30 秒、重复 3 轮执行首页第一页测试，并采集服务器 CPU、GC 和线程状态。
